Reflection

Quick note: “Actual” here means what the code is built to do. I haven’t saved a full live run in audit_trail.json yet, so I’m not making up any agent conversations.

How I would evaluate the agents

I think initially it was hard to evaluate whether agent has solve the task because of the way it was displayed - not very granular breakdown of what has been achived and what was not resolved; after the edit I asked the agent to display the results in a table format, it was easier to judge --- line by line item what was resolved or not

Expected versus Actual

  • 101 (tee order): I expected Boss → Inventory → Accounting → Customer Service, using get_customer_order_context. The setup matches that. I still need a live run to see the real order the agents go in. Cash shouldn’t move.
  • 102 (rent): I expected Boss → Facilities → Accounting, then a short note from Customer Service, using get_rent_notice_context. The agents can look at the rent, but they can’t pay it. One thing that’s off: the ticket gets marked “resolved” right after the run, even though nobody has paid the rent yet. Cash stays at $3,400 until a human approves.
  • 103 (hoodie discount): I expected Boss → Customer Service → Inventory and Accounting, using get_bulk_discount_context. The tool gives the key numbers: 20 wanted, 8 in stock, $22 cost, $58 list price. I still need a live run to check what the agents actually say. Cash shouldn’t move.

What would be simpler as one agent with tools?

Honestly, 101 and 103 could each be handled by one agent. The MCP tool already pulls all the facts together in one call, so passing the job between five agents doesn’t add much. It just makes it clearer who did what. 102 is where splitting makes sense, because reading the lease and dealing with money are different risks, and keeping them apart makes it harder to pay by accident. Either way, only a human should be able to move cash.

Three new problems the team could solve now

  1. Suggest a restock for 101: Inventory sees there are no size-S tees, and Accounting checks the $840 reprint invoice. The team suggests a restock. A human still has to approve buying anything.
  2. Check if we can pay rent (102): Facilities checks the due date, and Accounting checks the balance. The team can say “$2,400 rent, $3,400 in the bank, we’re fine,” but only a human can actually pay.
  3. Reply to the bulk order (103): Customer Service explains we only have 8 of the 20 hoodies, and Accounting works out how much room there is for a discount. A human signs off on the final quote.

Three problems the team cannot solve yet

  1. Actually order the tee reprint: There’s no tool for placing orders or talking to vendors. We’d need a purchasing tool, approval rules, and a record of each order.
  2. Actually send emails to the customer or landlord: The agents can write the message, but they can’t send it. We’d need an email tool and a “human clicks send” step.
  3. Actually hold or ship the 20 hoodies: There are no tools for reserving stock or shipping. We’d need a shipping agent plus tools to hold the 8 we have and source the other 12.
